# ДЗ 2. MongoDB — каталог и заказы

Сделал на Go с официальным драйвером (go.mongodb.org/mongo-driver/v2).
Сценарии из комплекта переписал в CLI-утилиту: данные, контракты и
контрольные значения не менял, датасет тот же (2026-10-05). Каждый сценарий
сам готовит свои данные и складывает фактический результат в
`results/results.json`.

## Как воспроизвести

```sh
make up        # поднять 3 узла mongo:8.0.30 и проинициализировать replica set
make fixtures  # посмотреть контрольные данные и эталоны
make data      # валидатор, поиск, история, отчёт
make index     # планы до/после индекса на 10 000 заказов
make purchase  # покупка, откат, повтор, конфликт
make failover  # смена primary
make all       # четыре сценария подряд
make down      # остановить (make clean — с удалением данных)
```

Каждая цель — это `docker compose run --rm app <команда>`. После правок кода
пересобираю образ командой `make docker-build`. Юнит-тесты без базы:
`make test`.

## Изменения окружения

compose.yaml взял из комплекта. Что поменял: добавил сервис `app`, который
собирается из Dockerfile и работает в той же внутренней сети стенда;
инициализацию replica set вынес в `deploy/init.js` (в комплекте это делал
lab.js). Базы (hw2, hw2_failover), URI, топология и версия MongoDB — без
изменений. Единственное отличие по настройкам: драйвер v2 не отправляет
`wtimeout`, для MongoDB 8.0 этот параметр устарел, его роль играет
`serverSelectionTimeoutMS` из URI. Остальное из приложения А сохранено.

## 2. Данные, модель и запросы

Валидатор: `$jsonSchema` на `products`, режим strict/error, ставлю через
collMod. Проверяет обязательные поля (`_id, name, category, price,
variants`), типы (`price` — decimal, `stock` — int/long), структуру
`variants` (items — объект с обязательными `size` и `stock`) и
неотрицательность (`minimum: 0` у цены и остатка). В опыте корректный
документ принимается, а документы со строковой ценой и с отрицательным
остатком отклоняются с кодом 121 — в `errInfo` видно, какое именно правило
не прошло (для цены, например, `consideredType: "string"`).

Поиск: `{variants: {$elemMatch: {size: …, stock: {$gte: qty}}}}`. elemMatch
нужен, чтобы размер и достаточный остаток относились к одному варианту, а
не к разным элементам массива. Контрпример из задания проходит: у A остаток
L=0, M=10, поиск `clothes/L/2` не возвращает A, после изменения остатка L
на 2 — возвращает.

История: find по `userId` и `status`, сортировка `{createdAt: -1, _id: 1}`,
limit 20. Равные даты у H-заказов упорядочиваются по `_id` по возрастанию,
пустой результат — пустой массив.

Про модель. Позиции встроены в заказ, потому что заказ всегда читается
целиком, позиции отдельно от заказа не существуют и никогда не запрашиваются
по одной. Одна покупка — одна вставка одного документа, ничего собирать и
согласовывать не надо. История покупателя при этом — отдельные
документы-заказы, а не массив в документе пользователя: заказы растут
неограниченно (массив рано или поздно упрётся в лимит 16 МБ), каждый заказ
живёт своей жизнью, а запрос истории — это фильтр, сортировка и лимит, под
которые нормально строится индекс (раздел 4). Цена в позиции — это факт
«сколько стоила единица в момент покупки». Текущая цена в каталоге
меняется, а суммы прошлых заказов меняться не должны, поэтому цена
копируется в позицию, и отчёт считается по ней. В опыте поменял цену A на
999.00 — выручка за январь не изменилась.

## 3. Отчёт о продажах

Pipeline: `$match` (paid и `createdAt` из `[from, to)` через `$gte`/`$lt`)
→ `$unwind $items` → `$group` по sku (`qty: {$sum}`, `revenue: {$sum
{$multiply: [qty, price]}}`) → `$lookup` на products за именем →
`$sort {revenue: -1, sku: 1}` → `$limit 5`. Умножение int на Decimal128
даёт Decimal128, точность не теряется. Весь расчёт на сервере, цикла в
приложении нет.

Расчёт товара A по позициям исходных заказов:

| Заказ | Позиция | qty | Цена | Сумма |
|---|---|---:|---:|---:|
| sale-start | A/M | 2 | 100.00 | 200.00 |
| sale-middle | A/L | 1 | 120.00 | 120.00 |
| Итого | | 3 | | 320.00 |

Проверил границы: заказ ровно в `from` входит (sale-start), ровно в `to` —
нет (excluded-end не попадает). Пустой период возвращает []. У A и B
выручка одинаковая (320.00), порядок по артикулу: A раньше B.

## 4. Индекс и план

Запрос истории `{userId: 2500, status: "paid"}`, набор 10 000 заказов.
hint не использовал.

| Вариант | nReturned | totalKeysExamined | totalDocsExamined | Есть отдельная SORT |
|---|---:|---:|---:|---|
| До индекса | 20 | 0 | 10000 | да (COLLSCAN → SORT) |
| После индекса | 20 | 20 | 20 | нет (IXSCAN → FETCH) |

Список `_id` и их порядок до и после совпадают и совпадают с эталоном,
посчитанным независимо по фикстурам.

Индекс `{userId: 1, status: 1, createdAt: -1, _id: 1}` построил по правилу
ESR: сначала поля равенства (userId, status), потом поля сортировки в её
направлении (createdAt по убыванию, _id по возрастанию). Поэтому индекс сам
отдаёт документы в нужном порядке. До индекса план — COLLSCAN: сервер
читает все 10 000 документов и отдельно сортирует их стадией SORT. После —
IXSCAN: сканируется 20 ключей, FETCH достаёт 20 документов, SORT исчезает,
limit применяется уже при сканировании. Издержка индекса — записи: каждая
вставка и обновление заказа теперь поддерживает ещё одно B-дерево по четырём
полям, то есть запись дороже и индекс занимает память на каждом узле.

## 5. Покупка

Как устроено. Сначала, до транзакции, читаю заказ по `_id = operationId`.
Если заказ уже есть и параметры совпали (userId и тройки sku/size/qty по
порядку) — возвращаю сохранённый заказ как есть, с его датой и ценами. Если
параметры другие — REQUEST_CONFLICT. Сравниваю по полям, поэтому порядок
ключей в JSON и изменившаяся цена каталога на повтор не влияют.

Если заказа нет, открываю одну сессию и одну транзакцию: readConcern
snapshot, writeConcern `{w: "majority", j: true}`, readPreference primary.
Дальше для каждой позиции updateOne с проверкой остатка в самом фильтре:
`{_id: sku, variants: {$elemMatch: {size: …, stock: {$gte: qty}}}}` и
`$inc: {"variants.$.stock": -qty}`. Если matched = 0 — товара, размера или
остатка нет, кидаю ITEM_UNAVAILABLE. Потом внутри той же транзакции читаю
цены и вставляю заказ (`_id = operationId`, статус created, позиции в
порядке входа). Ошибка в теле транзакции → abortTransaction, всё прошло →
commitTransaction. Обёртка — обычный txManager.Do(ctx, process), как в
наших сервисах на postgresе: process получает контекст с сессией.

Опыт с откатом: первый товар (A/M × 2) списывается по-настоящему, это видно
в трейсе (`update_inside_transaction`, sku A, modified 1), второй (B/L × 6
при остатке 5) не находится, транзакция откатывается — оба остатка
возвращаются к исходным, заказа нет.

Атомарность и защита от повтора — разные вещи, и делаются они по-разному.
Атомарность даёт транзакция: все изменения покупки применяются вместе или
не применяются вообще (это и показал откат). Защита от повторного
бизнес-запроса — это идемпотентность: тот же operationId, присланый второй
раз, не должен создать второй заказ и повторно списать товар. Транзакция
сама по себе этого не даёт, я делаю это через `_id = operationId` и
сравнение параметров до транзакции. Подтверждённый повтор вообще не открывает
транзакцию.

Счётчики serverStatus().transactions (снимки до/после каждого опыта, один
процесс, sameProcess = true):

| Опыт | Δ totalStarted | Δ totalCommitted | Δ totalAborted |
|---|---:|---:|---:|
| Успешная покупка | 1 | 1 | 0 |
| Откат после первого списания | 1 | 0 | 1 |

Получилось ровно по таблице задания, потому что транзакцией управляю сам,
без автоповторов драйвера.

## 6. Смена primary

Опыт: было m2 PRIMARY, m1 и m3 SECONDARY. Записал контрольный документ
"before" с majority и j:true — подтверждён. Вызвал
`replSetStepDown(60, secondaryCatchUpPeriodSecs 10)`: команда завершается
ошибкой, потому что уходящий primary рвёт соединения, это ожидаемо и
записано в артефакт. Дождался нового primary (им стал m1) и тем же самым
клиентом прочитал "before" и записал "after" с тем же write concern. Обе
операции прошли, в probe ровно 2 документа, повторов почти не понадобилось.

Клиент находит новый primary так: он создан по URI со всеми тремя адресами
и `replicaSet=hw2rs` и постоянно мониторит узлы. Когда старый primary
уходит, драйвер помечает его недоступным, реплика-сет проводит выборы, и
операции автоматически уходят на нового primary. Пересоздавать клиент или
менять адрес не нужно — достаточно повторить операцию, когда primary готов.

Почему majority-запись не гарантирует свежее чтение с любой secondary:
majority означает, что запись зафиксирована большинством узлов и не
потеряется, но репликация асинхронная. Конкретная secondary может ещё не
применить операцию, и чтение с неё вернёт старое состояние — это не
нарушение гарантий, просто отставание. Поэтому в опыте чтение идёт с
primary.

## 7. Шардирование

1. Для истории `{userId: 2500}` mongos опросит только шард B: в фильтре
   точное равенство по ключу шардирования, а 2500 попадает в диапазон
   [2000, 5000), который лежит на B. Для отчёта `{status: "paid"}` фильтра
   по ключу шардирования нет, поэтому запрос уйдёт на оба шарда, A и B, а
   mongos смёржит результаты.
2. Индекс `{status: 1}` число участников не изменит: маршрутизация зависит
   от ключа шардирования и метаданных распределения, а не от индексов.
   Польза от него в другом — внутри каждого шарда вместо полного перебора
   его куска коллекции будет IXSCAN по status. То есть работы на каждом
   участнике меньше, но fan-out на оба шарда остаётся.
